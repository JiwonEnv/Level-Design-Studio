# 08. 기술 규칙 — 코드가 지켜야 할 계약

[01-PRODUCT-SPEC.md](01-PRODUCT-SPEC.md)(무엇을 만드는가), [02-CURRENT-IMPLEMENTATION.md](02-CURRENT-IMPLEMENTATION.md) F절(테스트로 강제되는 계약), [03-DATA-FORMAT.md](03-DATA-FORMAT.md)(저장 형식)에 이미 적힌 내용은 반복하지 않는다. 이 문서는 그 세 문서에 없는 **구현 규칙·불변 조건·UI 원칙**만 담는다. 셋 중 하나와 충돌하면 01 → 03 → 02 → 08 순으로 우선한다.

표기: **[현재]** 지금 코드가 지키는 규칙 / **[후속]** 아직 구현되지 않았지만 구현할 때 반드시 따를 규칙.

## 1. 좌표·의존성

### 1.1 좌표 프레임
- 프로젝트 원점은 절대 오프셋이며 메시 피벗이 아니다. 에셋 변환(GLB/FBX 축·단위)은 배치 Transform 아래의 **별도 자식 프레임**이다. 어떤 단계에서도 원본 기하를 재중심화하지 않는다. [현재]
- 엔진 좌표 프로필(03 D.10)은 **검증한 FBX 수송 프로필**(Blender에서 -Z forward / Y up으로 내보낸 FBX)에만 유효하다. 다른 FBX 내보내기 설정에 그대로 적용된다고 가정하지 않는다. [현재]
- 회전 변환은 해당 프로필의 반사된 기저(reflected basis)를 쓴다. 축척은 축 순서만 바꾸고 **음수 축척을 주입하지 않는다**. [현재]
- 좌표 테스트는 길이 같은 스칼라 값이 아니라 **변환된 점 좌표**를 비교한다. 테스트 fixture의 원점은 bounding box 중심 밖에 두어 피벗 보존을 검증한다. [현재]
- Unreal 좌표 검증 스크립트는 FbxFactory를 명시 선택하고 그 commandlet 세션에서만 Interchange FBX를 끈다. 사용자 엔진 프로젝트 설정은 바꾸지 않는다. Interchange 경로는 이전 FbxImportUI 설정을 넘기면 1/100 크기로 들어올 수 있으므로, 실제 Unreal Importer를 Interchange로 만들 때는 **자체 설정과 별도 검증**을 갖춰야 하며 FbxImportUI 설정이 적용된다고 가정하지 않는다. [후속]
- `scripts/engine-validation/`은 좌표·가져오기 검증 도구일 뿐 장면 Exporter가 아니다. 이것을 엔진 출력 구현으로 표시하지 않는다.

### 1.2 의존성 그래프
- 간선은 원천 → 소비자 방향이다: parent→child, Reference→node, asset→node, entity→예약 output, Recipe→Variant/Instance, node→Instance, Instance→Slot, Slot→Part, owner→Socket. [현재]
- retired 상태의 production 레코드는 실시간 그래프에서 제외한다. `affectedBy`는 관계없는 output을 반환하지 않는다. [현재]
- 알 수 없는 변경 ID는 조용히 무시하지 않고 진단으로 돌려준다. [현재]
- `planGenerationForChanges`는 그래프 진단(누락·순환)이 하나라도 있으면 갱신 계획을 만들지 않는다. 진단이 없을 때만 영향받은 entity ID를 순수 생성 계획기(`planGeneration`)에 넘긴다. [현재]
- 영향 조회는 장면을 자동 편집하지 않는다. [현재]
- 상단 "연결 검사"는 영향받는 설계/출력 수와 이름을 보여 준다. 연결 진단과 앞으로 추가될 형상·충돌·보행성 검사를 화면에서 구분한다. [현재]

### 1.3 Socket
- `extensions.sockets`는 데이터 계약이다. 에셋 소유 Socket은 그 에셋을 배치한 node가 있어야 월드 포즈가 생긴다(에셋 단독에는 월드 위치가 없다). [현재]
- 도로·다리·건물 자동 스냅은 이 계약만으로 지원된다고 표시하지 않는다. [현재]

## 2. ID

03 D.9와 02 F절의 ID 규칙에 더해 다음을 지킨다.

- 검증 오류가 나도 ID를 **자동 수리하거나 재발급하지 않는다**. 이전에 손상된 문서가 강화된 검증에서 실패할 수 있으며, 이때 원래 저장 바이트는 기존 복구 경로로 열 수 있어야 한다. [현재]
- 현재 Override는 **객체 Transform만** 보존한다. 부품별·재질별 보존을 약속하는 UI 문구를 쓰지 않는다. [현재]
- `extensions.productionIdentity`는 명시적인 production identity 조작으로만 만든다. 이 확장이 없는 문서는 그대로 둔다. 편집·저장·재열기 때마다 검증한다. [현재]
- Recipe 파라미터를 고쳐도 Recipe ID는 바뀌지 않는다(데이터만 바뀜). [현재]
- Slot의 `semanticKey`는 **의미**(예: `floor:ground`, `facade:front`, `bay:entry`)를 나타내며 배열 인덱스가 아니다. 같은 키로 찾으면 같은 Slot ID를 돌려준다. 생성기가 키를 부여할 때는 편집 전후 의미를 유지해야 하고, 의미가 바뀌면 새 키를 쓴다. [현재 / 생성기는 후속]
- Part의 원본 에셋을 교체해도 Part ID와 별도 Override는 유지한다. [현재]
- 은퇴(retire) 규칙 [현재]:
  - 레코드는 이력용으로 남기고 지우지 않는다. 의존 작업을 조용히 삭제하지 않는다.
  - 활성 의존 레코드가 남아 있으면 은퇴를 거부한다. 의존 쪽을 먼저 은퇴시킨다.
  - 은퇴한 Slot을 자동으로 다시 활성화하거나 재사용하지 않는다.
  - 기준(anchor)이 사라진 것은 해결할 **충돌**이지 Override를 버려도 된다는 뜻이 아니다.
- productionIdentity는 ID와 저장만 담당한다. 건축 메시 생성, Recipe 규칙 평가, 필드 단위 Override 병합, Recipe 편집기는 별도 작업이다.

## 3. 장면 소유권

03 D.2~D.4(nodes 권위, projection 일치 검사)에 더해 다음을 지킨다.

### 3.1 책임 분리 [현재]
- 설계 도형(node/entity)과 생성 결과(`sourceEntityId`가 있는 object)는 같은 필드의 복제가 아니라 **서로 다른 책임**이다. 생성 결과의 기하·Transform·에셋·출처는 그 object가 원본이다.
- 이미지의 원본 픽셀 크기·축척 기준·불투명도·보정 근거는 Reference node의 `properties.referenceData`가, 월드 위치·Z 회전·축척·표시·잠금은 Reference node의 transform이 원본이다.
- 그룹과 draft는 메시가 없어도 저장·선택·수정할 수 있어야 한다.
- 레거시 footprint/recipe와 알 수 없는 확장 필드는 현 생성기의 새 원본으로 취급하지 않고, 임의로 삭제하지도 않는다.
- 저장 파일에서 호환 배열(entities/objects/references)을 제거하지 않는다.

### 3.2 변경 경계 [현재]
1. 공통 편집 순서: `CommandHistory` 트랜잭션 → `applyNodeCommand` → `projectLegacy` → `validateDocument`.
2. 기존 STEP 편집(호환 배열 수정)은 명령 전 snapshot과 비교해 **실제로 바뀐 행의 노드만** 반영한다. 바뀌지 않은 노드를 월드→로컬 역변환하지 않는다(역변환 오차로 손대지 않은 도형이 움직이는 것을 막기 위함).
3. 편집 가능한 원본을 두 벌 유지하지 않는다. `projectLegacy`가 매번 노드로부터 호환 배열을 만든다.
4. 불일치하면 어느 한쪽을 골라 저장하지 않고 거부한다. 원본·이전 저장본은 보존한다.
5. 설계 변경은 생성 미리보기/적용 정책을 따른다. 자동 재생성으로 사용자 편집을 지우지 않는다.
6. Undo/Redo는 프로젝트 전체 트랜잭션을 되돌리되 디스크 `revision`과 generation/checksum 저장 토큰은 **현재 값을 유지**한다. "저장된 시점"과 "이력 위치"를 구분한다.

### 3.3 개별 동작 [현재]
- 모델 연결 해제: 배치를 지우지 않고 같은 ID·Transform의 Prop draft(`extensions.detachedAsset`)로 남긴다. 연결이 없으므로 모델은 표시하지 않는다. 다시 연결하면 같은 ID로 복원한다.
- 잠긴 하위 객체를 포함한 그룹 삭제는 차단한다.
- 2D와 3D는 같은 effective visibility/lock 계산을 사용한다.
- 비균일 부모 축척 + 회전으로 shear가 생기면 작업을 롤백하고 이유를 보여 준다. 잘못된 월드 위치를 조용히 저장하지 않는다. 임의 shear 지원은 없다.
- Quaternion↔XYZ Euler 변환은 pitch ±90° 특이점을 처리해야 한다.
- `previousUnappliedTransform`이 있는 파일은 사용자 검토 대상이다. 이 값을 조용히 적용하거나 버리지 않는다.

## 4. 에셋 갱신 정책

01 9.2(제품 수준 버전 정책), 02 F절(트랜잭션·pin 계약), 03 D.5~D.6(형식)에 더해 다음을 지킨다.

### 4.1 원본 감지 [현재]
- 디렉터리 감시 이벤트는 **검사 힌트**일 뿐 진실의 원본이 아니다. 주기 검사·열기·수동 검사로 누락을 보완한다.
- 파일을 읽기 전후 stat이 다르면 기다린다. 같은 hash/size/mtime 관측이 안정된 뒤에만 분석한다.
- 안정화 시간은 저장 완료를 보장하지 않는다. 포맷 길이·chunk/buffer·구조 검사를 반드시 함께 한다.
- 재시작 시에도 원본과 현재 라이브러리 hash를 다시 비교한다. timestamp만 믿지 않는다.
- 같은 바이트면 변경 없음. 읽기 실패면 이전 파일과 pin을 그대로 둔다.

### 4.2 변경 분류 [현재]

| 변경 | 처리 |
|---|---|
| 지원 텍스처(PNG/JPEG/WebP) 내용 | 자동 갱신(포맷 완료 상태 확인 후) |
| UV, 같은 구조 안의 정점 형태 | 자동 갱신 |
| node frame / Pivot / FBX 단위·축 | 영향 검토 |
| Material Slot, 재질 연결·바인딩 | 영향 검토 |
| node·mesh·hierarchy, primitive 배치, 정점·인덱스 수 | 영향 검토 |
| 애니메이션, GLB required extension, 비교 정보 없음 | 검토 또는 분석 오류로 보류 |
| 불완전·손상 데이터 | 오류. 이전 정상 레지스트리·pin·blob 유지 |
| 원본 없음 | 누락. 라이브러리 사본으로 작업 계속 |
| 같은 폴더에서 같은 내용 발견 | 이동 후보. 사용자가 연결해야 복구 |

- 구조 정보를 추출할 수 없으면 "호환"으로 간주하지 않고 **unknown**으로 표시한다. sparse GLB 등 미지원 구조는 오류로 남겨 원본을 보호한다.
- FBX 자동 판정은 검증한 정적 exporter fixture 범위다. 모든 FBX 버전을 완전 지원한다고 표시하지 않는다.
- 자동 판정 임계값을 근거 없이 정하지 않는다.

### 4.3 검토와 적용 [현재]
- 검토 화면은 이름, 변경 이유, 영향받는 프로젝트·배치 수, 적용 / 나중에 / 취소를 제공한다.
- 적용 직전에 원본 hash와 기존 라이브러리 hash를 다시 확인한다. 확인 이후 바뀐 후보는 적용하지 않는다.
- 보류·취소는 같은 hash에 대해 재검사해도 다시 적용하지 않으며 재시작 후에도 유지한다. 내용이 새로 바뀌면 새 후보로 다시 판단한다.
- **현재 열린 프로젝트**: host에 active ID를 알려 백그라운드 commit 대상에서 제외한다. 렌더러가 승인 이벤트를 받아 같은 asset pin과 node `assetRefs` hash**만** 바꾸는 하나의 Undo 명령으로 실행하고, 기존 자동 저장 경로로 저장한다. 처리한 이벤트(`assetAutoEvents`)는 Undo/Redo와 저장에 유지해 Undo 직후 다시 적용되지 않게 한다.
- 메시 캐시는 object ID뿐 아니라 pinned hash도 키로 비교한다.
- **다른 프로젝트**: 각각 독립된 쓰기 잠금 → revision/generation/checksum 검사 → recovery 기록 → commit. `updatePolicy:'pinned'`면 건너뛴다. 실패·미결 복구·동기화 충돌이면 보류하고 이전 blob을 유지한다. 프로젝트마다 별도 트랜잭션이므로 일부 성공·일부 보류가 정상이다.
- 자동 반영은 ID·Transform·parent·layer·visibility·lock·수정(modification) 필드를 덮어쓰지 않는다. 단, 승인한 pivot/mesh 변경은 숫자 Transform이 같아도 화면 결과를 바꿀 수 있으므로 검토 화면에서 이를 알린다.

### 4.4 저장 순서와 보존 [현재]
1. 새 blob을 durable write한다. 같은 이름의 blob이 이미 있으면 hash를 검증하고, 손상된 blob을 덮어쓰지 않는다.
2. `.asset-history/<assetId>/<tx>.json`에 before/after와 `prepared`를 기록한다.
3. 외부 레지스트리 변경과 동기화 충돌 사본을 검사한 뒤, 고유 임시 JSON에서 전체 메타데이터를 원자 교체한다.
4. `committed`로 마친다. 이전 파일은 삭제하지 않는다.
- `.asset-monitor/state.json`은 캐시다. 없거나 읽을 수 없으면 원본과 라이브러리를 다시 비교한다. 정상 blob·프로젝트 commit의 권위는 이 파일이 아니다.

### 4.5 후속 기능을 만들 때의 규칙 [후속]
- 변경 처리 순서: 파일 변경 → 후보 바이트 → importer 구조 검사 → 의존성 영향 → 미리보기/확인 → 레지스트리 갱신. 감시 스레드는 프로젝트 문서를 직접 수정하지 않는다.
- Importer 구조 요약에는 bounds·단위·축·피벗·mesh identity·material slot 이름/개수·UV 채널·원본 object 대응을 포함하고, 포맷별로 신뢰할 수 있는 추출 범위를 기록한다. pivot/slot 변경, 분할·병합, 기준점 소실은 구조 변경으로 분류하고 영향받는 프로젝트 이름과 객체를 보여 준다.
- 영향 계획(ImpactPlan)에는 source hash, target hash, 영향받는 프로젝트/node/속성, Override 보호, 구조 차이, 확인 필요 사유, **검사하지 못한 프로젝트**를 포함한다. 적용 직전 프로젝트 generation/checksum을 다시 검사한다.
- 라이브러리 갱신과 프로젝트별 pin 적용은 별개 트랜잭션이다. 확인하지 않은 프로젝트는 기존 바이트를 계속 쓴다.
- 전용 → 공용 승격: 기존 파일을 이동·삭제하지 않는다. 같은 논리 ID로 공용 레지스트리에 등록하고 바이트를 검증해 연결한다. ID가 충돌하면 자동 재발급하지 않고 identity·범위·참조를 비교한다. 원래 전용 항목은 alias로 보존하고 참조가 안전하게 전환됐는지 검사한다. 모든 프로젝트를 검사할 수 없으면 검사 범위를 표시한다.
- 원본 파일(sourceFiles: .blend, 제작 텍스처)과 실행용 산출물(runtimeArtifacts: .glb/.fbx, 변환 텍스처)은 역할이 다르며 N:M 연결을 허용한다. 변환기 버전·원본 hash·옵션·산출물 hash를 기록한다.
- PC별 절대 경로는 로컬 locator로 분리하고, 공유되는 manifest에는 원본 identity와 상대/논리 경로만 기록한다.
- 사용 중인 에셋의 삭제는 사용처 확인 후 숨김·보관으로 처리한다(01 9.2). 실제 삭제·휴지통은 별도 설계 후 구현한다.

## 5. 동기화 경계

01 10절(Git+LFS 제품 결정)에 더해 다음을 지킨다. 원격 동기화는 아직 없다(02 C절).

### 5.1 현재 지켜야 할 것 [현재]
- 복구 기록·잠금·캐시·`.asset-monitor`는 PC 로컬 운영 데이터다. 클라우드 파일 동기화가 끝났다는 이유만으로 프로젝트가 유효하다고 간주하지 않는다.
- `.gitattributes`가 있다는 것과 LFS가 설치되어 실제 객체를 전송한다는 것은 다르다. 이 파일만으로 PC 간 동기화가 된다고 표시하지 않는다.
- blob 자리에 LFS 포인터만 있으면 원본이 준비되지 않은 것이다.
- 화면의 "저장 완료"는 **로컬 저장** 의미다. 원격이 없는 상태를 숨기지 않고 "동기화 연결 안 됨"으로 표시한다.
- OneDrive 충돌 사본은 Git merge와 다른 현상이다. 두 상태를 같은 "동기화 완료"로 합치지 않는다.

### 5.2 원격 동기화를 구현할 때 [후속]
- 프로젝트 저장소와 공용 라이브러리 저장소는 각자 remote·HEAD·마지막 동기화 지점을 가진다. **라이브러리를 먼저** 준비하고, 프로젝트의 pinned 바이트를 받을 수 있는지 확인한 뒤 프로젝트를 전환한다. 해당 hash의 내용이 준비되기 전에 참조만 바꾸지 않는다.
- 원격 받기는 임시 작업 영역에서 manifest·checksum·LFS 파일 준비 여부를 검증한 뒤 전환한다. 받기 전에 로컬 복구 가능한 snapshot을 유지한다.
- 기존 locator/commit 형식을 Git merge 도구로 간주하지 않는다.
- 동기화 예약기는 **성공한 로컬 저장 checkpoint**만 입력으로 받는다. 파일 이벤트마다 push하지 않는다. 저장 중, 감시 파일이 불안정할 때, 충돌 상태일 때는 원격에 반영하지 않는다. 묶음 간격·종료 시 처리 정책은 실제 시험 후 정한다.
- 대기열은 projectId, 로컬 generation/checksum, asset pin 목록, 마지막 동기화 commit, 재시도 상태를 지속 기록한다. 재시도가 최신 장면을 과거 사본으로 바꾸지 않는다.
- Git commit 성공과 LFS 업로드 성공을 구분하고 **둘 다 검증돼야** 동기화 완료다.
- 갈라진 경우 last-writer-wins를 하지 않는다. Object ID/속성 patch, 에셋 ID/hash, 생성 결과/사용자 수정 경계(Generated·Override·Independent)를 기준으로 비교한다. 한쪽만 바뀐 것은 자동 후보, 같은 속성을 양쪽이 바꾼 것은 확인 필요다.
- 충돌은 이름·배치·재질·규칙 등 사용자 용어로 비교하고 "내 작업 유지 / 받은 작업 사용 / 별도 사본으로 보관"을 제시한다. 양쪽 원본을 보존하고 선택 결과는 새 commit으로 만든다.
- force push, 임의 삭제, working tree 강제 초기화를 자동 해결책으로 쓰지 않는다.
- 프로젝트와 공용 라이브러리의 동기화 결과를 따로 표시한다. 화면에는 Git 명령 이름 대신 "저장 완료 / 저장 중 / 동기화 중 / 동기화 완료 / 동기화 실패 / 확인 필요"를 쓴다.
- 원격에 올리지 않는 것: 사용자 원본 절대 경로, 인증 정보, 로컬 프로필, recovery, cache, 오류 로그. Git 도입 전에 `sourceFiles`의 절대 경로를 portable manifest와 로컬 locator로 분리해야 한다.
- 두 PC, Files On-Demand, 오프라인 중 경로 이동, 전송 중 종료·다운로드 실패는 실환경에서 따로 검증한다.

### 5.3 소스 저장소 [현재]
- 소스 저장소에는 의존성 폴더, 빌드·설치 결과, 개인 Workspace, 사용자 절대 경로가 들어간 테스트 산출물과 프로필을 넣지 않는다. 테스트 증거가 필요하면 경로를 정리한 별도 보관본으로 둔다.

## 6. 지형 파이프라인

03 D.8(형식·계산 순서·한도)에 더해 다음을 지킨다. [현재]

### 6.1 계산
- `parameters.terrain`은 선택이다. 없는 지형은 기존 경계 폴리곤 면으로 계속 표시한다. 높이 계산을 켜는 것은 명시적 opt-in이다.
- IDW Base는 역제곱 거리 가중이며 제어점 위치에서 정확히 그 높이를 낸다. elevation은 한 번만 더한다.
- Profile 목표 높이는 Base 샘플 또는 로컬 기준면에서만 구한다. 이미 수정된 높이를 다시 읽지 않는다. stroke Profile은 경로까지의 **최소 거리**를 쓰므로 한 stroke 안의 자기 겹침은 한 번만 적용되고, 서로 다른 stroke는 명시 순서대로 누적된다.
- 각 Modifier는 영향 범위·영향 정점·높이 변화 범위를 보고한다. 활성 여부와 순서는 명시 데이터다.
- earcut 삼각분할 후 경계의 일직선 샘플점을 복원한다. 등고선 절단 교차점 정점은 이웃 삼각형과 공유한다. 등고선 뒤에 적용되는 Profile/Modifier가 그 등고선 높이를 바꾸는 것은 의도된 동작이다.
- 결과는 **렌더링용 heightfield**다. 내비게이션·구조해석용 메시로 표시하지 않는다.
- 형상과 Profile은 정규 node의 **로컬 미터 좌표**에서 계산하고 생성 결과에서 한 번만 월드로 변환한다. node의 회전·이동·축척은 생성 서명(signature)에 포함한다. 속성을 따로 월드 좌표로 복사하지 않는다.
- 계산 결과를 같은 지형의 Base로 되먹이지 않는다. 구성 요소의 의존성 주소는 소유 output에만 닿는다.
- 한도를 넘으면 진단을 내고 **이전 지형 결과를 유지**하며, 다른 유효한 생성 항목은 계속 선택할 수 있어야 한다. 설정 검증과 계산은 분리한다.

### 6.2 경계 방식
- 세 방식 모두 위쪽 지형 면은 동일하게 유지한다.
  - Cliff: 깊이와 바깥쪽 경사를 가진 측면.
  - Platform: 측면 + 가장 낮은 경계보다 요청 두께 이상 아래의 평평한 닫힌 바닥. 시계/반시계·오목 경계와 등고선 교차점에서도 모서리가 닫혀야 한다(일직선 샘플 복원).
  - Blend: 명시 기준면까지 이어지는 8개 링의 띠, 부드러움 조절.
- 확장 링은 자기 교차·원본 포함·교차 여부를 검사한다. 좁은 오목부·예각처럼 지원하지 않는 형상은 생성을 거부하고 이전 결과를 유지한다.
- surface/side/cliff/bottom/blend 파트 범위와 material slot 이름은 저장되며, 렌더러는 파트별로 법선·재질을 분리한다.
- 경계 규칙은 폴리곤 전체에 적용된다(변마다 개별 설정 없음). Profile의 falloff와 바깥 경계 생성기는 별개다. Blend는 기준면에 붙을 뿐 이웃 지형과 자동 접합하지 않는다.

### 6.3 2D 높이 편집
- 브러시 좌표는 연속값이다(미터 스냅 없음). 제어점·등고선 배치는 화면의 스냅 설정을 따른다.
- 브러시 stroke는 놓을 때 한 번만 commit한다. Esc·포인터 취소는 문서를 바꾸지 않는다.
- 선택 모드에서 제어점·등고선 정점을 옮겨도 ID는 유지된다.
- 폴리곤 밖 제어점, 서로 모순되는 등고선 높이는 원자적으로 거부한다. 등고선은 경계 밖으로 나가도 되며 교차하는 부분만 높이에 영향을 준다.
- 인스펙터 편집은 설계 데이터만 바꾼다. 기존 output은 STEP 3 미리보기·적용 전까지 그대로다.
- 잘못된 입력은 문서와 UI 바인딩을 **함께** 롤백한다. 다음 정상 입력은 복원된 모델을 기준으로 한다.
- 지형 전체 드래그는 정규 node 프레임을 바꾸며 소유한 높이 데이터가 함께 이동한다.
- 축척 보정 시 선택된 Terrain의 제어점·등고선·Profile의 XY, 반경, falloff, Blend 폭을 같은 트랜잭션에서 재투영한다. Z 높이, 깊이·목표 높이·경사, 계산 간격, 구성 요소 ID는 바꾸지 않는다.
- 기울어진 Terrain은 2D 높이 편집·보정에서 제외한다. Z축 회전과 지면 비균일 축척은 지원한다.

## 7. Reference 작업 흐름

01 5.1(축척 모드·원본 보존·보정 원칙)과 02 C절에 더해 다음을 지킨다. [현재]

### 7.1 이미지·레이어
- 활성 편집 대상은 항상 명시적이다.
- 새 이미지를 최상위에 넣으면 바뀌지 않은 다른 레이어의 순서 값도 함께 갱신한다.
- 일반 이미지를 가져올 때의 초기 폭(100m)은 **표시용 자리값**이며 미확정으로 표시한다. 미확정 이미지에 연결된 도형만 생성이 막히고, 관계없는 실측 도형은 계속 사용할 수 있다. 생성 계획을 적용하기 직전에 다시 확인한다.
- 지도 캡처의 좌표 축척과 기존 두 점 보정은 확정으로 인정한다. 폭만 있는 예전 이미지는 확정이 필요하다.
- 확정 처리 때문에 기존 기하·저장된 출력을 자동으로 크기 변경하거나 삭제하지 않는다.

### 7.2 축척 보정
- 폭 직접 입력과 두 점 보정 모두 **적용 전까지는 제안**이다. 캔버스에 제안된 이미지 경계와 선택 도형 외곽을 그리지만 문서는 바뀌지 않는다. 취소하면 버린다.
- 적용은 원본·연결 도형이 그 사이 바뀌었으면(stale) 거부하고, 통과하면 Undo 가능한 편집 하나로 기록한다.
- 도형마다 "미터 좌표 유지" 또는 "원래 이미지 픽셀 기준 XY 재투영"을 고른다. 기본값:
  - 미확정 상태의 첫 보정: 생성되지 않았고, 잠기지 않았고, 원본 Reference가 하나인 도형을 재투영 대상으로 기본 선택.
  - 이후 보정: 좌표 유지가 기본.
  - 잠긴 도형, 여러 Reference에 연결된 도형은 바꾸지 않는다.
- 폭을 직접 바꾸면 더 이상 맞지 않는 기존 두 점 보정 기록을 제거한다.
- 보정은 순수 영향 계획 → 도형별 선택 → 원자적 적용/Undo 하나 → 3D 자동 재생성 없음 순서를 지킨다. 영향받은 3D는 이후 생성 미리보기에서 갱신한다.

### 7.3 지도
- 지도 화면을 여는 것만이 타일 요청을 시작한다. 미리 받기·영역 스캔·오프라인 타일 저장·백그라운드 다운로드를 하지 않는다.
- HTTPS 전용, 줌 2–19. 일반 HTTP 캐시와 앱을 식별하는 User-Agent를 쓴다.
- 지도 화면과 캡처 PNG 모두에 출처 표기를 넣는다. 지도 로드 오류가 나면 캡처를 막는다. 오류가 정상 Reference를 빈 지도로 바꾸지 않는다.
- 캡처는 북쪽이 위인 기울임 없는 화면만 허용한다. 캡처 결과는 원본 PNG 에셋 + Reference이며 실시간 타일 묶음이 아니다. 저장된 PNG 픽셀 크기는 좌표 범위와 일치해야 한다.
- 날짜변경선을 넘는 캡처, 비평면·종횡비 불일치 캡처는 거부한다.
- 사용자가 나중에 Reference transform을 편집해도 원래 지리 출처 정보는 유지한다.
- 지역 미터 근사는 측량 좌표계나 지형·지오이드 변환이 아니다. 그렇게 표시하지 않는다.

### 7.4 PhotoCraft 처리
- 시스템 전역 설치를 하지 않는다. 앱이 동봉한 실행 파일만 쓴다.
- 백엔드는 허용 목록 명령만 실행한다. 렌더러는 실행 파일이나 임의 명령을 고를 수 없다.
- 입력 바이트는 등록된 프로젝트 hash에서 가져와 격리된 임시 사본으로 넘긴다. 셸 없이 인자 배열로 실행하고, 입출력 크기와 실행 시간을 제한하고, 결과 PNG 크기를 검증하고, 임시 파일을 정리한다.
- 미리보기는 에셋·문서를 만들지 않는다. 적용은 별도 PNG와 Reference를 만든다. 취소는 원본과 에셋 목록을 바꾸지 않는다. 원본 프레임/hash가 바뀌면 적용을 무효화한다.
- 파생 Reference의 의존성은 원본 Reference를 가리킨다. 크롭은 원본의 회전된 픽셀→월드 변환을 그대로 써서 확정 축척을 유지한다. 원근 보정은 새 실측 보정이 필요하며 지리·측정 근거를 물려받지 않는다.
- 같은 이미지 바이트는 에셋을 공유할 수 있지만, 프레임이 다른 지도·파생 결과는 별도 Reference 레이어를 만든다.
- PhotoCraft의 모든 기능이 Studio에서 된다고 표시하지 않는다.

### 7.5 OpenCV 후보
- 제한된 Node worker에서 실행한다. Python 설치를 요구하지 않고 렌더러 스크립트 제한을 완화하지 않는다.
- 원본 프레임/hash와 RGBA 길이를 확인한다. 투명 픽셀은 제외한다.
- 명암 기반 후보일 뿐 의미 인식(건물·도로 인식, 중심선 추출)이 아니다. `confidence`는 null이고 실제 윤곽/선 근거를 남긴다.
- 후보는 **픽셀 좌표**라 Reference 월드 프레임과 독립이다. 보정·이동 후에도 분석을 다시 할 필요가 없다. 대기 중 윤곽은 현재 프레임으로 그리고, 승인 시 그 프레임을 기록한다. 원본 내용/hash나 픽셀 크기가 바뀌면 새 분석이 필요하며 원래 분석 프레임은 provenance에 남는다.
- 미리보기는 에셋·entity를 만들지 않는다. "제안 저장"은 마스크 에셋과 분석 배치만 저장한다. 대기 윤곽은 원본 프레임이 현재와 같고 보일 때만 표시한다.
- **승인만** 설계 entity를 만들며 원본·후보 연결을 유지한다. 원본이 stale이면 승인을 막는다. 잘못된 기하, 없는 마스크·원본 참조는 거부한다.

## 8. 편집기 UI 디자인 원칙

01 3절·11절, 04의 화면 구성에 더해 다음을 지킨다. 외부 프로그램(Unity, Unreal, Blender, Substance Painter)은 **배치와 조작 방식**의 참고이며, 그 프로그램에 있는 기능을 자동으로 요구사항에 추가하지 않는다.

### 8.1 원칙
- 네 작업 공간 사이 왕복을 허용하고 같은 장면·객체의 선택과 상태를 이어간다. 앞 단계를 끝내야 다음 화면이 열리는 마법사 구조로 만들지 않는다.
- **선택 동기화**: 탐색기 행, 캔버스 강조, 속성 제목이 항상 같은 대상을 가리킨다. 어디서 선택해도 같은 속성이 열린다.
- **문맥 도구**: 지형·도로·건물 보조 도구는 관련 선택·도구에 맞춰 나타난다. 현재 도구와 편집 대상을 항상 표시한다. 브러시를 고르면 반경·강도 같은 값이 가까이 나타난다.
- 상단 문맥 도구와 화면(뷰) 조작을 분리한다. 도구 설정과 객체 데이터를 섞지 않는다.
- 검토 패널이 뷰포트를 덮지 않는다. 작업 모드와 종료 방법을 표시한다.
- 에셋 원본 편집과 장면 인스턴스 편집을 구분한다.
- **상태 가시성**: 저장 중/완료/실패, 선택 대상, 현재 도구, 적용 전 생성 결과를 구분해 보여 준다. 실패에는 복구 행동을 제공한다.
- **점진적 공개**: 자주 쓰는 속성을 먼저 보여 주고 정점 배열·연결·내부 식별자는 펼쳐야 보이게 한다. 일상 작업에 필요한 값을 고급 영역에 숨기지 않는다.
- **조작 거리와 목표 크기**: 자주 쓰는 조작은 작업 근처에 둔다. 체크박스는 이름을 포함한 행 전체를 클릭할 수 있게 한다.
- **그룹 구분**: 선택/이동, 그리기, 현재 도구 설정, 뷰 조작을 간격·구분선·제목으로 묶는다. 묶음 사이 간격을 묶음 내부보다 넓게 한다.
- **명암 대비**: 일반 글자 4.5:1, 큰 글자 3:1을 점검 기준으로 하고 필수 조작 경계·상태 표시의 비텍스트 대비도 점검한다. 색만으로 상태를 전달하지 않는다(문구·기호 병기).
- 아직 구현되지 않은 기능(예: STEP 3 Recipe/모듈 제작, STEP 4 단면·검사·출력)은 화면만 만들어 구현된 것처럼 보이게 하지 않는다. 실제 지원되는 기능만 활성화한다.
- 보기 설정 변경은 장면 편집 이력(Undo)을 오염시키지 않는다.

### 8.2 화면 골격
1. 상단: 프로젝트 표시·저장 상태·주요 메뉴.
2. 그 아래: 네 작업 공간 탭. 현재 선택된 탭과 제작 완료 상태를 혼동하지 않게 표시한다.
3. 왼쪽 탐색(객체/레이어/에셋), 중앙 캔버스, 오른쪽 선택 속성으로 역할을 고정한다.
4. 중앙 상단 작업 도구 → 그 아래 현재 도구 옵션 → 하단 조작 안내·좌표·스냅 상태.
5. 생성 검토 목록은 중앙 3D와 나란히 둔다(겹치지 않음). 작은 창에서는 보조 패널을 접되 복원 버튼을 남긴다.
6. 상세 로그는 접힌 보조 영역에 둔다. 저장 실패 같은 중요한 상태를 접힌 로그에만 남기지 않는다.

### 8.3 시각 규격 (출발값 — 대비·DPI·창 크기 검사 후 확정)

| 항목 | 기준 |
|---|---|
| 바탕 | 중립에 가까운 어두운 회색 3단계 표면. 작업 이미지·3D 결과와 경쟁하는 넓은 장식 면을 줄인다 |
| 강조색 | 연두색을 선택·주요 실행에만 쓴다. 성공/경고/실패는 문구·기호를 함께 표시 |
| 글자 | 기본 13px, 보조 12px, 패널 제목 13–14px, 화면 제목 16–18px. 작업에 필요한 값을 9–10px 글자에 넣지 않는다 |
| 간격 | 4px 단위(4/8/12/16/24px) |
| 조작 크기 | 일반 입력·도구 높이 28–32px, 주요 실행 32–36px. 작은 아이콘도 클릭 영역을 확보 |
| 경계 | 패널·입력·선택 경계의 역할을 구분. 모든 영역을 강조 테두리·카드로 감싸지 않는다 |
| 아이콘 | 선 굵기가 일관된 단일 계열. 처음 보는 도구는 한글 이름 병기 + 툴팁. 이모지·글꼴 기호를 섞어 쓰지 않는다 |
| 숫자 | 치수·각도·축에 단위를 표시. X/Y/Z 순서와 좌표 기준을 전 화면에서 통일 |
| 패널 | 고정 비율보다 최소 내용 폭과 캔버스 가시성 우선. 폭 조절·접기·기본 배치 복원 제공 |

- 색·글자·간격 값은 역할별 **토큰**으로 모으고, 기본/hover/선택/focus/비활성/오류 상태를 함께 정의한다. 화면마다 따로 값을 정하지 않는다.
- 최소 창·큰 창·125/150% 배율, 긴 한글 이름에서 이름과 핵심 조작이 잘리지 않아야 한다.

### 8.4 작업 공간별 배치

| 공간 | 중앙 작업 | 바로 보이는 조작 | 오른쪽 속성 | 고급/보조 영역 |
|---|---|---|---|---|
| STEP 1 Reference | 이미지·지도 탐색, 축척 확인, 보정·분석 결과 비교 | 자료 추가, 이동, 축척, 보정/분석 진입 | 선택 자료 정보, 축척, 투명도·표시·잠금 | 도형 트레이싱, 원본/파생 이력, 분석 세부값 |
| STEP 2 2D 설계 | 지형·도로·건물 자리와 연결 편집 | 선택/이동, 생성 도구 묶음, 현재 도구 옵션 | 선택 유형의 핵심 치수·규칙, 높이·폭·용도 | 정점 좌표 표(접힘), 상세 경계·연결·검사 보고서 |

| STEP 4 3D 편집·출력 | 같은 장면의 공간·충돌·보행성·최종 배치 확인 | 선택/이동/회전/크기, 화면 맞춤, 검사, 단면 | 선택 속성, 생성 결과 배치와 Override를 명시 구분 | 진단 상세, 출력 설정, 엔진별 검증 정보 |

### 8.5 UI 변경 시 확인할 흐름
- 이미지 등록 → 축척 → 도형 설계 → 생성 미리보기 → 일부만 적용 → 3D 검토 → 이전 공간으로 복귀.
- 탐색기·캔버스·생성 결과에서 같은 대상을 선택하고 속성·강조 표시가 일치하는지.
- 그리기·브러시 작업을 끝내거나 취소한 뒤 선택 모드로 돌아오는지.
- 잠긴 객체, 선택 없음, 생성 결과 없음, 미리보기 적용 전, 저장 실패 상태 각각.
- 여러 객체·작은 창·배율 변경에서 잘림과 캔버스 가림이 없는지.
- 보기 설정 변경이 사용자 데이터와 기존 결과를 보존하는지.
